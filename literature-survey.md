# Literature & SOTA Survey — Deadline and Contention Aware GPU Memory Scheduling for VLA Models

All sources below were retrieved and verified during a multi-pass research process (August-September 2026): an initial scouting pass (search-snippet/abstract level), followed by a dedicated full-text deep-read pass on the most load-bearing sources, followed by a final kill-search before committing to this scope. Verification level is stated explicitly per source — this project does not present snippet-level findings as full-text-verified fact.

### 0. Roh, Kim, Kim (AVEES Lab, Kookmin University). "OOM-Free Alpamayo via CPU-GPU Memory Swapping for Vision-Language-Action Models." *IEEE RTCSA 2026 (32nd Intl. Conf. on Embedded and Real-Time Computing Systems and Applications).* [arXiv:2605.11678](https://arxiv.org/abs/2605.11678) · [github.com/aveeslab/oom-free-alpamayo](https://github.com/aveeslab/oom-free-alpamayo)
**Primary technical foundation of this project — read in full text.** Fits NVIDIA's 22GB Alpamayo-R1-10B / Alpamayo-1.5-10B onto 12-16GB GPUs via three coordinated techniques: Sequential Demand Layering (stream layer weights on demand, dropping VRAM granularity from model-level to layer-level), Pipelined Demand Layering (a double-flat-buffer + dedicated prefetch CUDA stream overlapping H2D transfer with compute), and a GPU-Resident Layer Decision Policy (a one-time offline profiling run picks which layers stay permanently GPU-resident, to maximize throughput within a VRAM budget). Reported results: 4.09s on an RTX 5070 Ti (16GB), 15.46s on an RTX 3080 Ti (12GB) — both configurations OOM without this system. **The explicitly named gap this project targets**: the residency policy is static (computed once per machine, never revisited) and optimizes purely for throughput — it has no deadline parameter and no live sensing of GPU contention from another process. Code confirmed real, substantive, MIT-licensed, peer-reviewed venue artifact (not an unreviewed hobby repo) — cloned locally.

### 0b. NVIDIA (Alpamayo team). "Alpamayo: A Foundation Model for Physical AI Applied to Autonomous Driving." [arXiv:2511.00088](https://arxiv.org/abs/2511.00088)
**Read in full text — source of this project's real-time deadline number.** States directly: *"real-time performance (99 ms latency)"* and *"the decoding process must be fast enough to support real-time inference... within the real-time requirements for autonomous driving (typically 100ms)."* This 99ms/100ms figure was measured on a full-VRAM NVIDIA RTX 6000 Pro Blackwell GPU with no memory swapping — this project's own baseline (the swapped system above) is 40-150x over this figure, which is why this project's success criteria are framed around relative improvement and graceful degradation, not "achieving real-time" outright (see proposal.md §1).

### 1. "Nova." [arXiv:2509.21301](https://arxiv.org/abs/2509.21301)
**Read in full text — the closest mechanism-level near-miss.** Implements real layer-wise CPU-GPU weight offloading for a Vision Transformer encoder, using async CUDA streams, pinned memory, and CUDA events — the same core mechanism family as OOM-Free Alpamayo. Scoped entirely to GUI/agentic-VLM serving on desktop GPUs (RTX A6000/4090); its "real-time" framing balances its own internal bursty request stream, not resistance to an independent second workload. **Confirmed absent from the paper: any mention of "robot," "VLA," "control loop," or an external/co-located contention source.** Necessary prior art for the swapping mechanism; does not cover the deadline- or contention-adaptivity this project adds.

### 2. "RED: Adaptive Real-Time DAG Scheduling for Robotic Inference." [arXiv:2605.24044](https://arxiv.org/abs/2605.24044)
**Read in full text.** Deadline-aware scheduling for *multiple already GPU-resident* DNN tasks on Jetson-class embedded GPUs, using MIMONet weight-sharing across tasks; treats out-of-memory as an exception state to avoid, not something to actively manage via layer streaming. **Operates at a different layer entirely**: inter-task scheduling among models that already fit, not intra-model memory management for one model that doesn't fit. No overlap with this project's contribution.

### 3. "FASTER." [arXiv:2603.19199](https://arxiv.org/abs/2603.19199)
**Read in full text.** Accelerates the flow-matching action-generation/denoising steps inside a VLA model — a different part of the inference pipeline (the math itself, not memory placement). Contains one passing mention of "memory contention" in its limitations section, nothing more. No overlap.

### 4. "Action Chunk Scheduling for Batched Robot Policy Serving." [arXiv:2608.00337](https://arxiv.org/abs/2608.00337)
**Read in full text.** Schedules which robot, among a fleet, gets served from one remote/shared GPU — inter-robot request scheduling, not intra-model memory management for a single oversized model. No overlap.

### 5. "Efficient Block-Layer Parallel Inference for Vision-Language-Action on Hybrid Architectures." [arXiv:2608.14586](https://arxiv.org/abs/2608.14586)
**Found in the final kill-search pass, read at abstract level — the newest and closest real competitor, must be cited and differentiated explicitly.** Partitions a driving VLA model's backbone so the LLM suffix runs on CPU via an async cross-frame pipeline; tested on two real driving VLA models (Orion, MindDrive) under real-vehicle "coexistence" with the rest of the onboard compute stack. Reports 21.7-30.9% latency reduction (521ms→408ms, 443ms→306ms) and peak GPU memory reduction (45GB→29GB for Orion). **Key distinction, stated precisely**: this is a static CPU/GPU compute-*placement* split, decided once and validated as a fixed architectural choice — nothing in the abstract indicates the partition point adapts live to a sensed deadline or to a second, independently competing workload. This paper is strong evidence the underlying problem (large driving-VLA models vs. real hardware memory/latency budgets) is a live, multi-group-hot area in 2026, which strengthens rather than weakens this project's motivation — but it does not close this project's specific gap (live-adaptive residency under sensed deadline and contention pressure). A full-text read of this paper before final submission is recommended to confirm this distinction holds beyond the abstract.

### 6. Kütükçü, Baidya, Raghunathan, Dey. "Contention Grading and Adaptive Model Selection for Machine Vision in Embedded Systems." *ACM TECS 2022.* DOI: [10.1145/3520134](https://doi.org/10.1145/3520134)
**Read in full abstract (previously verified during this student's earlier GPU-scheduling research, now archived — see `IAS/research/archive-old-gpu-scheduling-project/`).** Source of the "Artificial Contention Unit" (ACU) technique — dummy GPU workloads generating a controllable, steady contention level — reused here as the methodology for this project's synthetic GPU-contention injection experiments (see proposal.md §2).

### 7. "Embodied Foundation Models at the Edge: A Survey of Deployment Constraints and Mitigation Strategies." Grover et al. [arXiv:2603.16952](https://arxiv.org/abs/2603.16952)
**Read at summary/abstract level only — do not cite beyond what's stated here.** Frames VLA-at-the-edge deployment as fundamentally a systems problem via an "eight coupled barriers" framework, and states autoregressive VLA policies are specifically memory-bandwidth-bound (as opposed to diffusion-based controllers, which are compute-latency-bound). Cited as corroborating context that this is a recognized, named problem class, not as a source of any specific unverified claim beyond this summary.

---

**Summary of the gap this project targets:** the mechanism (CPU-GPU layer swapping to fit an oversized model) is not new — OOM-Free Alpamayo and Nova both do it well. What no surveyed source does is make the *residency decision itself* a live function of (a) a real control-loop deadline budget and (b) sensed contention from an independently co-located second GPU workload, for a VLA model. RED and Action Chunk Scheduling address deadline-awareness at a different layer (inter-task/inter-robot, not intra-model memory). The newest close competitor (#5) addresses the same domain problem via a different, static mechanism (compute placement, not memory residency) validated once, not adaptively. This project's contribution is the live-adaptive residency policy, built as a direct extension of a real, peer-reviewed, publicly available codebase.
