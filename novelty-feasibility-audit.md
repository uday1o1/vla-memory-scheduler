# AI Novelty & Feasibility Audit — Deadline and Contention Aware GPU Memory Scheduling for VLA Models

This audit was run as two separate, adversarial passes (novelty and feasibility), following the standard practice of actively searching for reasons the idea fails or already exists, rather than reasons it works — the same standard applied to this student's other two projects. This project itself replaced an earlier CMPE 249 topic (concurrent GPU scheduling for radar/ISAC + perception workloads, archived at `IAS/research/archive-old-gpu-scheduling-project/`) after the student determined the domain, not the technical style, was the reason to change direction; several rounds of scouting, deep-reading, and kill-searching preceded this final audit.

## AI Critique Summary (Deliverable D)

*This is the AI's own critique, distinct from the audit-trail narrative below.*

Is this genuinely novel? Yes, narrowly. The mechanism (CPU-GPU layer swapping to fit an oversized model) is not novel — a real, peer-reviewed system (`oom-free-alpamayo`, IEEE RTCSA 2026) already does it well, and a closely related system (Nova) does the same core trick for desktop VLM serving. What's not found anywhere, after full-text-reading five close candidates and running a dedicated kill-search, is making the layer-residency *decision itself* a live function of a real deadline budget and sensed GPU contention, for a VLA model specifically. A genuinely new, close competitor (a June 2026 paper on block-layer parallel inference for driving VLA models) was found during the final audit pass — it addresses the same underlying problem but via a different, static mechanism, and must be cited and explicitly differentiated, not ignored. Real, disclosed weaknesses: this project should not claim it achieves true real-time (~100ms) inference — even the best-resourced 2026 competitor doesn't get there; success is framed as relative improvement over the existing static baseline, not an absolute deadline hit. The foundation being extended is a small (88KB) codebase from one paper — real and peer-reviewed, but a solo student should verify early that its documented extension point (the residency-decision function) is as cleanly isolated in practice as its documentation suggests.

## Novelty Audit — Verdict: SURVIVES WITH NAMED LIMITATIONS

**Why it survives.** Five close candidates were read in full text (literature-survey.md #1-5) and a dedicated kill-search (including checking whether `oom-free-alpamayo` itself has already been forked or cited by a follow-up work — confirmed no: its one GitHub fork is an unmodified mirror with an identical push timestamp, and it has zero Semantic Scholar citations as of this audit) found no source combining (a) deadline-awareness, (b) live GPU-contention-awareness, and (c) intra-model memory-residency decisions, for a VLA model. Nova does (a real version of) the swapping mechanism without deadline/contention framing; RED and Action Chunk Scheduling do deadline-awareness at a different layer (inter-task/inter-robot scheduling among already-resident models, not memory management for one oversized model); FASTER accelerates a different part of the pipeline entirely.

**Named limitation 1 — a real, close, newly-found competitor must be cited, not ignored.** A June 2026 paper ("Efficient Block-Layer Parallel Inference for VLA on Hybrid Architectures," literature-survey.md #5) addresses the same underlying problem (large driving-VLA models vs. real hardware memory/latency limits) via a static CPU/GPU compute-*placement* split, validated once on real driving VLA models under real-vehicle coexistence testing, reporting 21.7-30.9% latency reduction. This project's contribution must be stated precisely relative to it: a *live-adaptive memory-residency* policy reacting to a *sensed deadline and contention signal at runtime*, not a static, offline-validated compute-placement decision. This paper was only read at abstract level in this pass — a full-text read is recommended before final submission to confirm the distinction holds (e.g., confirm it truly never adapts its partition point at runtime).

**Named limitation 2 — mechanism vs. contribution.** CPU-GPU layer swapping itself is not novel (OOM-Free Alpamayo, Nova both do it). The claimed contribution is specifically the *policy* governing residency decisions under deadline and contention pressure — this must be stated explicitly and repeatedly in any presentation of this work, the same discipline already applied in this student's other two projects.

**Named limitation 3 — the sourced deadline number needs precise framing.** The ~100ms real-time figure comes from Alpamayo's own paper, measured on a full-VRAM RTX 6000 Pro Blackwell GPU — not the swapped system, and not a realistic rented GPU. Stating this number as if it were the swapped system's own original target would overclaim; the proposal (§1) already frames success criteria relative to the static baseline's own achievable range instead, which is the honest framing to keep.

## Feasibility Audit — Verdict: SURVIVES WITH NAMED LIMITATIONS

Based only on verified resource facts (no duration/time estimates used to make this determination):

- **Model and code access, fully verified 2026-09-07:** `nvidia/Alpamayo-R1-10B` is real, ungated, permissively licensed (OpenMDW-1.1 — "free of charge, to deal in the Model Materials without restriction"), 22.16GB actual weight size confirmed via the HuggingFace API (directly confirming the "doesn't fit on 12-16GB" premise this project depends on). `aveeslab/oom-free-alpamayo` is real, substantive (not a stub — verified via its own file tree and README, which shows real measured benchmark output), MIT-licensed, actively maintained. Its upstream dependencies (`NVlabs/alpamayo1.5`, `NVlabs/alpamayo`) are both real, public, Apache-2.0-licensed, and actively maintained. All five repositories are cloned locally.
- **Compute access — reuses a previously-resolved finding, not a new open question.** Testing the contention-aware half of this project's claim requires running two processes on one GPU simultaneously (the inference process + a synthetic contention generator), which needs CUDA MPS administrative access. This exact requirement, and its resolution, was already established for this student's prior GPU-scheduling project: MPS-in-Docker support is provider-dependent; RunPod's root/full-OS pod model is the confirmed-reliable choice, gated by a mandatory pre-registration smoke test before committing to any provider. The same gate applies here.
- **Compute cost, revised down from the prior project:** this project involves no model training (Alpamayo is used frozen) — only a bounded evaluation sweep (baseline vs. adaptive policy × 2 contention scenarios × ≥8 repetitions). Estimated **$40-150** on a rented A100-class GPU, smaller than either of this student's other two projects' budgets.
- **Data access:** the model and code require no special access at all. Representative driving-scene inputs have two real, verified paths: NVIDIA's `PhysicalAI-Autonomous-Vehicles` dataset (auto-gated, fast approval, though its license's "Purpose" clause is a plausible-not-certain fit for a systems study — mitigated by needing only a small sample, not the full dataset) or the community `alpamayo-carla-bridge` project (real, substantive — verified by inspecting its actual file contents and README, not just its existence — which sidesteps the licensed-dataset question entirely via live CARLA simulation).
- **Engineering lift, assessed honestly:** more tractable than this student's other two projects, not less — the codebase being extended is small (88KB) and the original authors already isolated the exact extension point (a single "GPU-Resident Layer Decision Policy" function) by their own design, rather than requiring the student to carve out that boundary themselves.
- **Credibility of the foundation, addressed directly:** `oom-free-alpamayo` is not "just a GitHub repo" — it is the released artifact of a paper accepted at IEEE RTCSA 2026, an established embedded/real-time-systems venue. This should be stated explicitly in any presentation of this work, not left implicit.
