# Project Proposal — CMPE 249, Fall 2026

**Title:** Deadline and Contention Aware GPU Memory Scheduling for Vision-Language-Action Models
**Team:** Uday Arora
**Track:** Deployment Track — CMPE 249's own wording ("optimize a model for latency, memory... edge compute") is a direct, literal match for this project's content.

## 1. Problem Formulation

**Domain problem.** NVIDIA's Alpamayo is a real, open, 10B-parameter Vision-Language-Action model for autonomous driving; its weights are 22GB (independently verified via HuggingFace), exceeding the 12-16GB VRAM common on automotive/consumer GPUs. A real, peer-reviewed system, `oom-free-alpamayo` (IEEE RTCSA 2026), fixes this by streaming model layers between CPU and GPU on demand, with a one-time offline profiling pass deciding which layers stay permanently GPU-resident to maximize throughput. It works — reported inference times of 4.09s (RTX 5070 Ti) and 15.46s (RTX 3080 Ti), both configurations that OOM without it. But Alpamayo's own paper states autonomous driving needs ~100ms end-to-end latency to be real-time — a 40-150x gap. The residency policy that makes the model *fit* has no concept of a deadline, and no awareness of whether a second workload is simultaneously using the same GPU (a realistic condition on any platform running multiple AI services). Five close candidates were checked in full text (literature-survey.md #1-5); none combine deadline-awareness, contention-awareness, and intra-model memory-residency decisions for a VLA model — the closest (#5, June 2026) does a static CPU/GPU compute-placement split validated once, not a live-adaptive memory-residency policy.

**Honest framing, stated up front.** This project does not claim it will make Alpamayo hit true ~100ms real-time inference — even the newest, best-resourced competitor's static approach (#5) only reaches 306-408ms on real driving VLA models with far more engineering investment than a solo semester project can match. The claimed contribution is a **relative** one: does making the residency policy deadline- and contention-aware measurably reduce the deadline-miss rate and produce more graceful degradation under contention, compared to the existing static policy — not "solves real-time," but "meaningfully closes part of the gap in a way the current system doesn't attempt."

**Input/output specification.**
- *Input:* Alpamayo-R1-10B's normal inputs (multi-camera frames + optional trajectory history), plus two new signals the current system doesn't use: (a) a per-call deadline budget (a stand-in control-loop period, since 100ms itself is unreachable — see below), and (b) a live GPU-contention estimate (via NVML/DCGM, or a known injected level during controlled experiments).
- *Output:* the model's normal trajectory + reasoning output, plus a per-call record of which layers were kept GPU-resident for that call and the resulting latency, for analysis.

**Target metrics / success criteria (fixed in advance).**
- *Primary metric:* deadline-miss rate — the fraction of inference calls exceeding a stated per-scenario latency budget — for the adaptive policy vs. the unmodified static `oom-free-alpamayo` baseline, under injected GPU contention. The budget itself is scaled from the swapped system's own achievable range (not the unreachable 100ms figure) — e.g., defined relative to the static baseline's own median latency per scenario, so "miss" means "meaningfully worse than the system's own achievable floor," a concrete, falsifiable, non-moving-target definition fixed before data collection.
- *Secondary metric:* degradation curve shape under increasing contention (does the adaptive policy degrade more gracefully, e.g., smaller latency variance, than the static policy, which has no mechanism to react at all).
- *Statistical test:* paired Wilcoxon signed-rank test (same convention as this student's other two projects), effect size as matched-pairs rank-biserial correlation, ≥8 repetitions per scenario, α=0.05.
- *Power caveat, stated explicitly:* one model family, small n — this reliably detects only large effects; disclosed up front, not discovered after a null result.
- *Contention scenarios:* (1) steady compute-bound load, using Artificial Contention Units (literature-survey.md #6); (2) bursty load, injected via a second process at randomized intervals. Both run as an independent second process under CUDA MPS, gated by the same pre-registration smoke test used in this student's prior GPU-scheduling work (MPS-in-Docker is provider-dependent; RunPod's root/full-OS pod model is the confirmed-reliable option).
- *Null-result framing (fixed in advance):* if the adaptive policy shows no statistically detected improvement over the static baseline, that is reported precisely as "no statistically detected difference" — a valid, fully reportable outcome given this is genuinely unexplored territory.

## 2. Proposed Technical Approach

**Foundation.** Fork `aveeslab/oom-free-alpamayo` (real, MIT-licensed, cleanly modular — a `ModelAdapter` interface and a documented hook-based pipeline, with the exact extension point, the "GPU-Resident Layer Decision Policy," already isolated as one function by the original authors). This project modifies that one policy; it does not rewrite the swapping mechanism itself (Sequential/Pipelined Demand Layering), which is existing, correctly-functioning infrastructure.

1. **Baseline.** The unmodified upstream static residency policy, run exactly as released — a real, running baseline, not a reimplementation.
2. **Adaptive policy (the contribution).** Replace the one-time offline profiling decision with a policy that re-evaluates residency at runtime using (a) remaining deadline budget for the current call and (b) a live-sensed GPU-occupancy signal, choosing to keep more or fewer layers resident (and shift the prefetch schedule) accordingly. Concretely: under low contention/high budget, behave like the static baseline (near-optimal already); under high contention/tight budget, prioritize whichever layers most reduce worst-case latency variance, even if that's not the global throughput optimum.
3. **Contention injection.** Artificial Contention Units and a bursty-arrival generator (literature-survey.md #6), run as an independent process sharing the GPU via CUDA MPS.
4. **Evaluation.** Both policies run under both contention scenarios, ≥8 repetitions each, on the same hardware, same model, same inputs — differing only in the residency policy.

**Data sources.** The model (`nvidia/Alpamayo-R1-10B`, open, ungated, permissive OpenMDW-1.1 license) and the codebase (`oom-free-alpamayo`, MIT) require no special access. For representative input frames, two options, both real and verified: (a) NVIDIA's `PhysicalAI-Autonomous-Vehicles` dataset — auto-gated (fast approval, not manual review), though its license's stated "Purpose" (developing AV/ADAS systems) is a plausible-but-not-explicitly-confirmed fit for a memory-systems study, so only a small sample would be pulled, not the full 1700-hour set; or (b) the community `alpamayo-carla-bridge` project, which drives Alpamayo inside the open CARLA simulator — sidesteps the licensed dataset question entirely and additionally provides a real closed-loop testbed if time allows. Both are already cloned locally for evaluation.

**Intended technical modifications.** A runtime-adaptive layer-residency policy (replacing a static one); a deadline-budget and GPU-contention sensing layer feeding that policy; a contention-injection harness (Artificial Contention Units + bursty generator) reusable from this student's prior scheduling work; an evaluation pipeline comparing deadline-miss rate and degradation-curve shape, not just raw throughput.
